Result: NECESSARY

That verdict applies to `metrics_lock` as used in `metrics_on_request_processed()`, which is where the concurrency-critical section is. But the mutex actually guards two structurally different accesses to `processed_requests`, and they don't have the same status — worth separating them explicitly, since that distinction is exactly what a syntactic/alias-only analysis would miss.

**Increment site — `metrics_on_request_processed()` — NECESSARY.** `main()` spawns 8 threads, each running `worker_thread()`, which calls `handle_request()` 10000 times; every call ends in `metrics_on_request_processed()`, so you get 80000 calls to `processed_requests++` interleaved across 8 threads with no ordering between them (no barrier, no join, until the very end). `processed_requests++` is a read-modify-write — load, increment, store — not a single atomic step at the language level, regardless of what instruction a given ISA might compile it to. Without the lock, two threads can read the same value, both increment, both write back, and one increment is silently lost; run unlocked, the final printed count will typically land measurably below 80000, and by a different, nondeterministic amount each run. That's the practical symptom. Formally it's worse: under C11 §5.1.2.4, unsynchronized concurrent access to the same object where at least one access is a write is a data race, which makes the program's behavior undefined — not just "wrong count" but UB that a compiler is entitled to exploit under the assumption of race-freedom. This lock cannot be removed without breaking correctness.

**Read site — `metrics_get_processed()`, as called from `main()` — SEMANTICALLY USELESS in this program.** The only call to it is in `main()`, and it happens after the loop that calls `pthread_join()` on all 8 threads has fully returned. `pthread_join()` is a POSIX synchronization point: the terminating thread's memory operations happen-before the corresponding `pthread_join()` returns in the joiner. Once all 8 joins have completed, every write each worker made to `processed_requests` (correctly serialized among themselves by the lock in the increment path) is guaranteed visible to `main()`, and there is no other thread left alive that could write it concurrently with this read. So at that call site, the lock/unlock pair around `long v = processed_requests;` isn't providing any visibility or ordering guarantee beyond what the join already gave you — removing just that pair changes nothing about this program's observable behavior, on any execution.

The important qualifier is that this is a property of the call graph, not of the function in isolation. `metrics_get_processed()` is exported via `metrics.h` as a general API; if some other call site polled it from a monitoring thread while workers were still running, the lock there would be necessary again. A purely syntactic/escape-based check ("`processed_requests` is written from multiple threads, therefore every access must be locked") can't see that this particular call site is safe — it has to model the happens-before edge that `pthread_join()` introduces and tie it to this specific, join-gated call site. That's precisely the kind of path-sensitive fact an SMT-backed path validator earns its keep on, and it's what separates SEMANTICALLY USELESS from a trivially, syntactically provable USELESS lock (e.g. one guarding a variable that never escapes its owning thread, or a dead critical section) — this one requires reasoning about execution order, not just aliasing.

**Why not USELESS overall:** a strict USELESS verdict would fit a lock that no execution could ever need concurrency protection for — e.g. guarding stack-local data, or a global only ever touched before any thread exists. That's not this program: `processed_requests` is genuinely mutated from up to 8 concurrent threads, so at least one of the two guarded accesses is unconditionally required. Calling the whole thing "useless" and stripping the mutex entirely would reintroduce a real, demonstrable race.

If this is going into your CRUX test corpus, it's a clean minimal case for empirical corroboration: compile with `-fsanitize=thread`, drop the lock in `metrics_on_request_processed()` only, and TSan should reliably flag a race on `processed_requests`; drop only the lock in `metrics_get_processed()` while keeping the increment-site lock, and TSan should come back clean, since the join loop fully orders the read after every write by construction.
